# UI : la Vertical Slice s'applique aussi aux composants Svelte

```
create-invoice/
  ui/
    InvoiceForm.svelte
    InvoiceLineItem.svelte

reconcile-bank-statement-line/
  ui/
    reconciliation.svelte.ts             # Factory d'état réactif et méthodes métier
    reconciliation.test.ts               # Tests unitaires de la logique pure sans DOM
    BankStatementReconciliation.svelte   # Composant racine (composition & wiring, <= 300 lignes)
    ReconciliationHeader.svelte          # En-tête, sélecteur de saison et métriques
    BankTransactionsList.svelte          # Liste et filtres des lignes bancaires
    ReconciliationDetailPanel.svelte     # Panneau de détail et onglets d'actions
    ImportStatementDialog.svelte         # Modal d'importation OFX/CSV
    MatchTransaction.svelte
    CreateTransactionFromBankLine.svelte
    ReconciliationSummary.svelte

shared/ui/                # composants génériques réutilisés dans le domaine (rares)

libs/ui/                  # design system générique multi-domaine (Button, Modal, Table...)
```

## Exemple concret

`libs/domains/accounting/bank/reconcile-bank-statement-line/ui/BankStatementReconciliation.svelte` est découpé selon le pattern Svelte 5 :
- `reconciliation.svelte.ts` : encapsule l'état réactif (`$state`, `$derived`), le filtrage et les requêtes HTTP `fetch`.
- `BankTransactionsList.svelte`, `ReconciliationDetailPanel.svelte`, `ReconciliationHeader.svelte`, `ImportStatementDialog.svelte` : sous-composants spécialisés.
- `BankStatementReconciliation.svelte` : composant racine léger (< 300 lignes).

Même logique appliquée sur les autres slices complexes (`CheckDepositManager.svelte`, `SettingsManager.svelte`, `ExpensesManager.svelte`).

## Découpage des composants & Règle des 300 lignes

Pour tout composant Svelte complexe de domaine :
1. **Extraction de l'état** : L'état réactif (`$state`, `$derived`) et les interactions réseau `fetch` sont encapsulés dans un fichier `[nom].svelte.ts` via une fonction factory `create[Nom]State(props)`.
2. **Sous-composants dédiés** : Le rendu visuel est découpé en sous-composants ciblés dans le dossier `ui/`. Les sous-composants reçoivent l'état via props.
3. **Limitation de taille (Principe 11 étendu)** : Tout fichier `.svelte` doit faire **au maximum 300 lignes**. Aucun fichier du dossier `ui/` ne doit dépasser **400 lignes**.
4. **Tests de Logique Pure** : La logique métier contenue dans les fichiers `.svelte.ts` est testable unitairement avec Vitest en mockant la fonction global `fetch`.

## Règle de structure

Un composant Svelte spécifique à un cas d'usage vit dans `<domaine>/<cas-usage>/ui/`. Seuls les composants réellement génériques (bouton, modale, table, input) vivent dans `libs/ui/`. Les apps (`admin`, `storefront`) continuent d'importer ces composants via le barrel `index.ts` ou `shared/ui.ts` du domaine.

## Le design system : jetons, jamais couleurs en dur

Aucun fichier applicatif n'écrit une couleur. Les composants consomment des **jetons sémantiques** — `background`, `foreground`, `primary`, `muted-foreground`, `destructive`, `success`, `warning`, `border` — définis par application dans son `global.css`, en clair comme en sombre. Un jeton dit *à quoi sert* la couleur ; une valeur en dur ne dit que ce qu'elle vaut, et casse le thème sombre au premier oubli.

`libs/design-system.test.ts` en fait une règle vérifiée : il parcourt les composants Svelte des domaines, ainsi que les pages, composants et layouts des trois applications — **`apps/website` compris** — et échoue sur toute couleur de palette écrite en dur. Ajouter une application sans l'inscrire dans `scanTargets` la ferait échapper au contrôle.

### La charte du club, sur le site public

`apps/website/src/styles/global.css` est la source de vérité de la charte. Elle est remise par le secrétariat en cinq couleurs : **rouge `#E53345`**, **noir `#000000`**, **gris `#686768`**, **bleu `#15B9EC`**, **blanc `#FFFFFF`**.

Deux de ces cinq sont **claires** : le bleu tient 2,3:1 sur blanc, le rouge 4,3:1. Ni l'un ni l'autre ne peut donc porter du petit texte en thème clair, et les poser tels quels sous un libellé blanc passerait sous le seuil AA. La règle appliquée est la suivante : **chaque couleur est reprise exacte là où sa luminance le permet** — le noir en pied de page, le bleu en thème sombre, le rouge en aplat large — **et déclinée d'un ton ailleurs**. L'écart est invisible à l'œil, et c'est ce qui rend le site lisible dans les deux thèmes.

| Jeton | Valeur | Pourquoi |
|---|---|---|
| `primary` | rouge assombri d'un ton | Blanc dessus à 5,2:1, là où le rouge pur plafonne à 4,29:1 — juste sous le seuil d'un texte de bouton |
| `muted-foreground` | gris de la charte, **exact** | 5,6:1 sur blanc |
| `accent` | bleu de la charte à 8 %, texte foncé dédié | Le bleu pur ne peut pas porter de texte |
| `destructive` | rouge plus profond et plus froid | Le rouge est ici la couleur de l'**action principale**. Sans cet écart, une alerte et un bouton « Envoyer » porteraient la même teinte, et le rouge cesserait de vouloir dire quoi que ce soit |
| `success`, `warning` | hors charte | Un site a besoin de dire « c'est fait » et « attention » |

Les ratios notés en commentaire dans `global.css` sont mesurés **contre le fond sur lequel le jeton s'emploie**. Les mettre à jour fait partie de toute modification de la palette.

**Typographies**, auto-hébergées — aucun appel à un CDN de polices :

| Rôle | Police |
|---|---|
| Texte courant et titres | Montserrat Variable |
| Accent manuscrit | Yellowtail |
